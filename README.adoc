HWR OOP Rummikub Gruppe 3


This repository contains a student project created for an ongoing lecture on object-oriented programming with Kotlin at HWR Berlin (summer term 2026).

WARNING: This code is for educational purposes only.
Do not rely on it!


== Feature Liste
Steine:
- Generierung der Steine und ueberpruefung der Steinanzahl und Farben
Folgen:
- Folgen sind richtig (Anzahl der Steine, Farbe, aufeinanderfolgende Zahlen)
- Test - Man kann Steine zur Folge hinzufuegen - vorne und hinten
Sets:
- Sets sind richtig (Anzahl der Steine (dreier Sets und vierer Sets), unterschiedliche Farben, gleiche Zahlen)
- Sets sind ungueltig (Anzahl der Steine ist falsch (2>=x>=5)Farbe ist doppelt, unterschiedliche Zahlen)
- Sets Bearbeiten: Hinzufuegen zu 3er-Set (= gueltiges 4er-Set) und Hinzufuegen zu 4er-Set (= ungueltiges Set)
- Sets Bearbeiten: Wegnehmen vom 3er-Set (= ungueltiges Set) und Wegnehmen vom 4er-Set (= gueltiges 3er-Set oder gueltige Folge)
Spieler:
- Spieler hat einen Namen und ID
- Spieler hat Board(kann ziehen und Stein wird aus dem Beutel entfernt)
Beutel:
- Beutel kann existieren
- Beutel hat 104 (ohne Joker) Steine
- Steine ziehen funktioniert korrekt (Stein Anzahl minus 1)
Tisch:
-Gültige Kombinationen aus Sets und Folgen werden auf dem Tisch geprüft und angelegt
-passende Kombi kann aufgelöst werden
Spiel
- Züge werden auf Gültigkeit geprüft
- Auslegen: Die Punkte der Steine werden addiert. Ein Spieler darf Steine ab einem Gesamtwert von >= 30 Punkten auslegen
- aufloesen: Ein Spieler darf bestehende Kombinationen aufloesen, sobald er herausgekommen ist
- anlegen: Ein Spieler darf Steine anlegen, sofern er bereits mit >= 30 Punkten ausgelegt hat. Die angelegten Steine werden aus der Hand entfernt und der jeweiligen Kombination hinzugefügt
- ziehen: pro Zug zieht der Spieler einen Stein aus dem Beutel

Alle oben genannten Features sind getestet

Offen:
(+) 30 Punkte zum Rauslegen (Zählen + Züge zulassen) pro Spieler
- Test für 30 Punkte
(+) Spielzug gueltig
- Gewinnen/ Spiel beenden
- Highscore/ übrige Punktzahl zählen pro Spieler
- TODO rausnehmen/ bearbeiten
(+) Read-me anpassen
- SpielTest auseinanderziehen

- Test-coverage
- Mutations-coverage

- applications: UI-Verbindung
- Persistence: Speichern und Laden
(- Joker)
- Formatierung Code vor Abgabe

== Arbeiten mit dem Template-Repository (Upstream)

Dieses Projekt ist ein Fork des Template-Repositories.
Das Template bleibt als `upstream` eingebunden, damit Aktualisierungen daraus uebernommen werden koennen.
Die eigene Fork bei GitHub ist `origin`.

=== Schritt 1: Fork erstellen

oeffne das Template-Repository auf GitHub und klicke auf *Fork*.
Damit entsteht eine eigene Kopie unter deinem GitHub-Account.

=== Schritt 2: Fork klonen

[source,bash]
----
git clone https://github.com/DEIN_USER/TEMPLATE_FORK_REPO.git
cd DEIN_REPO
----

Nach dem Klonen ist deine Fork automatisch als `origin` eingetragen.

=== Schritt 3: Template als Upstream hinzufuegen

[source,bash]
----
git remote add upstream https://github.com/IT25A/hwr-oop-project-group3-rummikub
git remote add upstream https://github.com/stefreschke/hwr-oop-project-template-rummikub.git
----

=== Remotes pruefen

[source,bash]
----
git remote -v
----

Erwartete Ausgabe:

....
origin      https://github.com/DEIN_USER/TEMPLATE_FORK_REPO.git (fetch)
origin      https://github.com/DEIN_USER/TEMPLATE_FORK_REPO.git (push)
upstream    https://github.com/stefreschke/hwr-oop-project-template-rummikub.git (fetch)
upstream    https://github.com/stefreschke/hwr-oop-project-template-rummikub.git (push)
....

=== aenderungen aus dem Template uebernehmen

Wenn das Template aktualisiert wurde, kannst du die aenderungen wie folgt in deine Fork uebernehmen:

[source,bash]
----
# Neueste aenderungen vom Template holen
git fetch upstream

# Template-aenderungen in deinen main-Branch mergen
git merge upstream/main
----

Bei Konflikten muessen diese manuell aufgeloest und dann committed werden:

[source,bash]
----
# Konflikte beheben, dann:
git add .
git commit -m "chore: merge upstream changes"
git push
----

[NOTE]
====
Alternativ zu `git merge` kann auch `git rebase upstream/main` verwendet werden.
Rebase ist idiomatischer, da es eine lineare Commit-History erzeugt – in der Praxis ist es jedoch etwas aufwendiger zu handhaben, vor allem bei Konflikten.
Fuer dieses Projekt empfehlen wir daher, auf dem eigenen Fork einfach zu mergen.
====

== Docker und PostgreSQL

=== Docker installieren

Docker Desktop kann unter https://www.docker.com/products/docker-desktop/ heruntergeladen und installiert werden.
Nach der Installation muss Docker Desktop gestartet sein, bevor die folgenden Befehle ausgefuehrt werden koennen.

=== PostgreSQL-Datenbank starten

Eine lokale PostgreSQL-Datenbank ist ueber Docker Compose vorkonfiguriert:

[source,bash]
----
just start-db
----

Die Datenbank ist anschließend unter `localhost:5432` erreichbar (Verbindungsdaten siehe `applications/config.json`).

=== PostgreSQL-Datenbank stoppen

[source,bash]
----
just stop-db
----

Um die Datenbank mit einem *frischen Zustand* (alle Daten geloescht) neu zu starten:

[source,bash]
----
just discard-db
just start-db
----

== SQL-Tests aktivieren

Die Tests, die Docker und PostgreSQL benoetigen (`SqlPersistenceTest`, `ServiceSqlTest`, `CliSqlTest`), sind initial mit `@Disabled` annotiert.

Sobald die SQL-Persistenz implementiert ist, kann die Annotation entfernt werden:

[source,kotlin]
----
// @Disabled("Requires Docker")  // <-- diese Zeile entfernen
@Testcontainers
class SqlPersistenceTest { ... }
----

Danach benoetigt `just test` eine laufende Docker-Instanz.
